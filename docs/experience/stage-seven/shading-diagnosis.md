# Stage seven — bounded shading and macro-depth diagnosis

Reviewed 2026-09-08 against starting checkpoint `dbb8197`, runtime **Three 0.185.1**, installed types **0.185.4**. No checkout edits, browser launches, dependency changes or external assets. Line numbers below are from the source read before the owner's integration and may shift afterward. The two candidate TS files are original procedural code. Their types and CPU geometry/source contracts pass; **they are not GPU-compiled or visually accepted yet**.

The largest demonstrated defects are shadow sampling/bias at the wrong scale, missing cell shadow casters, and inconsistent custom-shader output/alpha handling. Correcting those gives the material and contact geometry a chance to read. Raising exposure or map resolution is not the first fix.

## Input/output and environment audit

- **Correct inputs:** `commercial.ts:58–65` and `site.ts:21` label Canvas colour textures sRGB; `earth.ts:56` labels day sRGB and clouds NoColorSpace. Pinned `WebGLTextures.js:230–234` selects SRGB8_ALPHA8 for byte colour textures, so their samplers decode to working-linear; do not manually pow-decode them in custom shaders. `region.ts:17` colours and instance colours created with `THREE.Color` are already working-linear. Standard/Physical hooks retain their built-in output path (`meshphysical.glsl.js:216–221`).
- **Correct renderer policy:** `scene.ts:82–86` uses default byte output, ACES exposure 1.04 and SRGB output. `WebGLProgram.js:771–779` provides functions/macros, but fragment main must actually invoke the chunks. Linear uniforms sent to custom shaders without the output chunk differ from the same colours in PBR/Basic materials. This is material-specific; changing global exposure cannot reconcile it.
- **PMREM is already linear:** `site.ts:25–29` renders the original sky/light card into PMREM. Pinned `PMREMGenerator.js:293–300` creates HalfFloat/LinearSRGB targets, `344–347` temporarily disables tone mapping and `440` restores it. `WebGLRenderer.js:2342` uses the working colour space for ordinary render-target output. The sky shader's raw palette is interpreted as linear radiance in that pass; the card's CSS colour is converted by THREE.Color. **Do not relabel the PMREM as sRGB or gamma-correct the stored radiance.** If changing its authored palette to CSS colours, convert them once at input.
- **Reflection scale, not a PMREM encoding bug:** `scene.ts:289` reduces environmentIntensity from .48 on the site to .10 in cell space. Glass clearcoat and the high-metalness contacts rely on this environment. The drop may contribute to dark, flat macro metal, but resolve pane geometry/contact shadows first and judge a small local reflection adjustment afterward. Keep environment rotation consistent with the existing transformed Sun.
- **No new HDR post pipeline:** the candidates use linear working inputs and the correct output conversion, but the default direct byte-canvas additive blend is still performed on output values. This is not a claim of physically exact scene-linear HDR compositing. A HalfFloat output target/post chain adds resources and is unnecessary for this bounded fix.

## Candidate files and integration

1. `shading-candidates.ts`: `filterSolarFineDetail(surfaceFragment)`; `filterCellFineDetail(siliconMaterial)` once per material; `configureCellMacroDepth(cell.group)` after prepare; straight-linear pulse/trail and EnergyFlow shaders; `withLinearOutput()` for existing single-exit cell overlays. Add `uTint: {value:new THREE.Color(...)}` to the candidate shader uniforms. Candidate EnergyFlow fragment must be paired with `energyFlowVertex`. Configure each selected overlay through `configureLinearAdditive()`; choose depthTest deliberately for the existing rear section explanation.
2. `aperture-pane.ts`: construct one geometry for glass and one for encapsulant from current `CX,CZ,GLASS_W,GLASS_D` and layer y/thickness. Own them in CellScene's geometry set; use plain Mesh with existing materials. In `sectionGeometry`, call `.setAperture((W+.20)*section,(D+.28)*section)` for both. Retain renderOrder 2/3 and the current externally attached backing/frame. Dispose these owned geometries normally. Each pane is **32 triangles  / 2240 GPU-buffer bytes  / one draw**, versus four box instances; no new texture or target.
3. Do not apply the output helper to the PMREM source shader or the already-managed Sun/Earth materials. `withLinearOutput` rejects early main returns; fullscreen transition rewriting needs all branches explicitly managed if the owner chooses to alter it.

CPU/type checks: strict `tsc` against installed pinned Three types passes. `check-candidates.mjs` verifies 0→tiny→full→reverse pane area, non-overlapping top coverage, outward winding, no non-finite vertices and stable backing arrays; confirms zero original cell casters versus four selected candidate casters; checks shader replacements preserve the existing output chunks. **No browser/GPU compilation or physical-device result is claimed.** Root should inspect the entry, partly open aperture, absorption, contacts and return under all three framings, then check source/Sun detail while stopped and moving.
